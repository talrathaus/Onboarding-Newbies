# Object Storage (S3-Compatible) – Client Perspective

Object storage systems expose a simple HTTP-based API for storing and retrieving data as objects.

From a client perspective, S3-compatible storage provides a unified way to interact with data regardless of the underlying implementation or vendor.

:warning: **Note:**  
This chapter is written strictly from the **client point of view**.  
We focus on how applications interact with the system not how it is implemented internally.  
We refer to **S3 and S3 compatible APIs**, for example using **Ceph** as interface.

# S3 Client Core Concepts

### ❓ Guide Questions

1. **Data Model, API, and Access Control:** Explain the flat namespace model of S3 (buckets, objects, keys, versions) and how it differs from a hierarchical file system. Explain why the namespace is flat rather than directory-based, what operations a client can perform using the S3 API, What are the different Storage Classes and compare how access is authorized at the client level using S3 API mechanisms (Bucket Policies, ACLs) versus user identities.

Objects: הנתונים עצמם בשילוב עם הmetadata, קובץ מסוים שיש לו מידע וKey.
Keys: המזהה הייחודי של אובייקט.
Buckets: המקום שבו נשמרים כל האובייקטים שלנו בצורה unstructured, הגבול העיקרי עבור מדיניות גישה, quotas וכללי replication.
Object version: הגרסא של אובייקט
ההבדל בין flat namespace לdirectory based הוא שdirectories בflat namespace הם לוגים לעומת directories בhirerchical namespace שהם פיזים.
הnamespace הוא flat כי אנחנו נרצה לעשות scale בצורה אינסופית לbucket שלנו ולכן לא נרצה להקצות משאבים שיכולים להשתנות לפי directory.  
בנוסף, אנחנו נרצה לעשות scale לפי הכמות שאנחנו צריכים ולכן נעדיף לא להגביל את עצמנו לdirectories.
create bucket, delete bucket, list buckets, put object, delete object(s), get object, restore object, list objects.
Storage classes: דרכים להגביל את היכולות של הS3 שלנו תמורת שיפור יכולות אחרות או הוזלה במחיר התחזוקה
S3 Standard – נתונים הנגישים בתדירות גבוהה
S3 Standard-Infrequent Access – נתונים הנגישים בתדירות נמוכה
S3 One Zone-Infrequent Access – אחסון נתונים בAvailability Zone יחיד במקום בשלושה (ברירת המחדל)
S3 Glacier Instant Retrieval – נתונים בארכיון הדורשים גישה מיידית
S3 Glacier Flexible Retrieval – אחסון בעלות נמוכה
S3 Glacier Deep Archive – אחסון בעלות נמוכה עוד יותר, לשמירה לטווח ארוך
Bucket Policy: שליטה בגישה לBucketים, והגדרה מראש כללים מסוימים הקשורים אליהם:
- מי רשאי לקרוא אובייקטים המאוחסנים בBucket
- מי רשאי ליצור אובייקטים המאוחסנים בBucket
- האם כל האובייקטים בBucket יהיו מוצפנים
ACL: ניהול הגישה לbuckets ולאובייקטים.  
לכל bucket ואובייקט מוצמדת ACL כמשאב-משנה.  
היא מגדירה אילו חשבונות או קבוצות מקבלים גישה, וכן את סוג הגישה.
IAM מאפשר שליטה על מי יכול לעבור authentication וauthorization לשימוש במשאבי S3.

2. **Durability, Distribution, and Failure Handling:** Explain how object stores achieve durability at scale through replication or erasure coding, how data and metadata are distributed across nodes, and how failures are detected and repaired. Why is distribution important for availability and resilience?

Replication: המידע בצורה דיפולטיבי נשמר ב3 [ברירת מחדל] availability zones [איזור פיזי שבו המידע נשמר] כך שגם אם אחד מהם נופל יש לנו מקום אחר להשיג ממנו את המידע וגם מקום לשחזר ממנו את המידע [restore-object].
Erasure coding: תהליך שבו הנתונים מחולקים לshards [חלקים קטנים], ומתווספים אליהם parity shards המשמשים כגיבוי.
אם חלק מהshards נאבדים עקב כשלים בחומרה או בעיות אחרות, S3 יכול להשתמש בshards הנותרים כדי לשחזר את הנתונים המקוריים.
זיהוי שגיאות קורה ב2 צורות:
- בדיקות Checksums: בעת העלאת נתונים, S3 מחשב ומאחסן ערך checksum, בדיקה זו תזהה bit rot או שיבוש בנתונים
- Auditing: סריקות רציפות על צמתי האחסון כדי לזהות חריגות ולתקן בעיות
התאוששות מאסון: S3 מסוגל לשחזר מקטעי נתונים שאבדו באמצעות Erasure Coding בצורה אוטומטית מבלי לפגוע בזמינות השירות.

3. **Large Object Uploads and Client Workflow:** How does a client upload large objects to S3 using multipart upload, what are the typical part-size and file-size considerations, and how does this affect client workflow and performance?

Multipart upload בS3 מפרק קבצים גדולים לחלקים קטנים יותר, המועלים במקביל.
Typical part size: 5MB to 5GB
Typical file size: עד 5TB
זה מקצר את זמן ההעלאה שלנו ומשפר את הסיכויים שכל הקובץ יעלה ולא יגרום לנפילה של הnode שמקבל את כל הקובץ לבד.

4. **Lifecycle, Retention, and Governance:** Explain how a client can configure S3 Lifecycle rules to manage data retention, delete markers, and cleanup of incomplete multipart uploads, what are S3 Object Lock (WORM) policies and how they are used to manage cost, compliance, and long-term storage. How do these features support archival and recovery workflows?

אפשר להגדיר Lifecycle rule שאומר שמידע צריך להימחק אחרי X זמן או לא להימחק.
delete marker בS3 הוא placeholder עבור אובייקט בעל גרסאות, אשר צוין בבקשת DELETE פשוטה.
S3 תומך בחוק Bucket Lifecycle, המאפשר להורות לS3 לעצור העלאות multipart uploads שלא הושלמו בתוך מספר ימים מוגדר ממועד תחילתן.
Object lock חוסם מחיקת גרסת אובייקט במהלך תקופת שמירה המוגדרת על ידי הלקוח.  
ניתן להשתמש בObject lock בכדי לממש WORM או לממש מחיקה לאחר X זמן.
משתמשים בפיצרים אלו בכדי להגדיר שאפשר למחוק מידע אחרי X זמן ובכך לחסוך בעלויות אחסון כאשר אפשר.
בנוסף, אפשר להשתמש בהם בשביל להגדיר שמידע נמחק בגלל סיבות חוקיות או להגדיר שהמידע לעולם לא נמחק.
הפיצרים האלו גם מאפשרים לעשות recover למידע שנשמר בS3 ולאחר מכן נפל בתהליך העיבוד.
